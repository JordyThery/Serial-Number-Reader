# Serial Number Reader: instructions for Claude

At the start of every conversation, run ../JTKit/Scripts/check-versions.sh (or fetch it from GitHub if ../JTKit isn’t there) and mention the result in one line if anything is out of date.

Shared code and the standards for every app: see JTKit's CLAUDE.md and ROADMAP.md (github.com/JordyThery/JTKit, or ../JTKit in the workspace).

## What the app does

A macOS app that identifies iPhones, iPads and Macs connected over USB by serial number, including devices that won't boot (Normal, Recovery and DFU mode). It looks them up in Jamf Pro (directly or through the Jamf Platform API) or Jamf School, and optionally in Apple Business or Apple School Manager, can edit the asset tag, and can switch modes and restore over USB (Restart, Enter DFU, Enter Recovery, Boot to Normal, Restore, Revive, Remove Trust). For admins and repair staff handling devices without a readable printed serial.

## How to work on it

- App-only work: open `Serial Number Reader.xcodeproj`. This folder's notes load and it builds against the published JTKit.
- Anything that changes JTKit: work in `~/Developer/Apps.xcworkspace`.
- Never have the app open in both at once.
- Build releases from the app's own project, so they use the published JTKit version.
- After merging into main, push main to origin straight away (keep GitHub in sync).
- Jordy is not a programmer: explain changes in plain language, in small steps.

## Architecture

All sources are in one folder, `Serial Number Reader/`.

- USB: `USBDeviceMonitor` (IOKit arrival/removal, mode from the product ID; the UI reads only this), `USBDevice`, `DescriptorParser` (Recovery/DFU serial descriptor, UDID normalizing), `ModelDatabase` + `AppleDeviceModels.json` (CPID/BDID → model; update the JSON for new hardware, no code change).
- Booted devices: `Usbmux` (usbmuxd + lockdown: unpaired device info, Enter Recovery), `LockdownTLS.m` (TLS on the lockdown socket for paired sessions; the device's certificate must be the pair record's `DeviceCertificate` or be issued by its `RootCertificate`).
- Power and mode actions: `DeviceActionController` (runs every action, one at a time, app-wide), `USBCPort` (which USB-C port a device is on: the IORegistry chain, read without privileges; `LiveUSBCPortRegistry`, or made-up data in tests), `PrivilegedVDM` (the root side: arguments and the chain check, before `VDMTool`), `VDMTool.mm` + `AppleHPMLib.h` (USB-PD VDMs for Restart / Enter DFU, to one port controller), `RecoveryCommands.m` (Boot to Normal), `DeviceReturn` (`DeviceReturnWatch`: after Restart, Enter DFU and Restore, waits for the same ECID in the expected mode, never the restore OS 0x12AC; the `AppDelegate` gives it the monitor's list), `DeviceReturnBanner` (the bar above the details: each device waited for, by name, how long, Stop Waiting, then the result until dismissed). `BridgingHeader.h` exposes the Objective-C parts.
- Restore: `Configurator` (runs Apple Configurator's `cfgutil`), `RestoreController` (the running job, IPSW checks against ipsw.me), `RestoreViews`.
- Jamf: `JamfClient.swift` (`JamfService`, `JamfConfiguration`, `JamfDeviceRecord`, the app's own error hints; computers are looked up only for a device that could be a Mac, `USBDevice.computerLookup`: a known model decides, and a device in Recovery or DFU whose model isn't in the list is looked up as a computer too), `JamfConnection`, `JamfStore` (lookups per device, asset tag, Test Connection), `LegacySettingsConversion` (runs into the Jamf list only, before the shared list reads it).
- Apple Business and Apple School Manager (optional, contributed by Everette G. Allen in pull request #1): `AppleBusinessConnection` (a saved API account: name, service, client ID, key ID), `AppleBusinessStore` (lookups per serial number on JTKit's `ABM.Client`: device, assigned device management service (skipped for an unassigned device; a failed request keeps the device, as for AppleCare; the service names are read once per client and again when a lookup meets an unknown service ID, at most once per lookup), AppleCare coverage; the portal link; Test Connection, failing with `ConnectionTestError` when the editor's values are incomplete; an incomplete account in use shows `.incomplete` with what's missing and Open Settings; the Apple role; demo mode uses JTKit's `Connection.demoAppleBusiness` only, as the demo Apple School Manager shares its name with the demo Jamf School), `AppleActivityRelay` (the Apple client records into its staging log; each entry moves to the app's log with the order number and the reseller's ID marked as identifiers, so the bug-report export masks them), `AppleBusinessText` (status, purchase source, coverage and CSV wording; `statusKind`: only Assigned is green, Unassigned orange, the rest neutral). The detail view shows the section only while an Apple account is in use or demo mode is on; the serial number is in the Device section only.
- Connections adapter (`AppConnections.swift`, as Checkpoint's): `AppConnection` (`.jamf` / `.apple`, the services and service groups, so a connection never switches between Jamf and Apple), `AppConnectionStorage` (the two UserDefaults lists, each loaded on its own: when one can't be read the other still loads, the unreadable one is copied, never written, a save into it is refused, and Settings › Connections says so (`listProblem`); only when neither can be read does JTKit's store refuse everything; a list whose entries didn't change is never written), `AppConnectionSecrets` (each secret in its own Keychain service under the connection's UUID; JTKit's account `apple/<UUID>` only picks the Apple store), `AppConnectionStore` (JTKit's one `ConnectionStore<AppConnection>`, shared by `JamfStore` and `AppleBusinessStore`; the Jamf connection in use and the Apple account in use). Two roles: `JamfStore.connectionRole` ("Jamf", Jamf services only) and `AppleBusinessStore.connectionRole` ("Apple", Apple Business and Apple School Manager only). Settings › Connections shows both in one list (`SettingsView`); the Connection menu has a section per role; the toolbar has the Jamf picker and, once an Apple account is saved or in demo mode, the Apple picker (decided by Jordy on 2026-11-10).
- UI and app: `MyApp` (one `AppConnectionStore` for the launch, `AppDemo.connections`; the `AppDelegate` owns the `USBDeviceMonitor`, `RestoreController` and `DeviceActionController` and links them, so neither starts while the other runs; the Device menu takes the detail view's actions through a focused value, `DeviceMenuActions`, on the same conditions as the buttons, `DeviceActionAvailability`), `ContentView`, `DeviceDetailView`, `SettingsView`, `AboutInfo` (About and the acknowledgement), `SessionExport` (CSV with the Apple status and device management service columns, copy all serials), `PreviewSupport` (Xcode previews: demo mode, no device, no saved connection).
- `BlockingWork` runs blocking USB work and child processes on their own threads; `ProcessOutput` drains both pipes.
- Demo mode: `AppDemo` (JTKit's `DemoMode`, saved under `demoMode`, and the sandbox run), `DemoUSB` (the pretend iPhone, `PretendIPhone`: `DemoWorld` device 42, `ZZDEMOP42RX`, in Contoso Jamf Pro), `USBHardware` (the one doorway to real devices: lockdown, iBoot, VDMs, `cfgutil`; `LiveUSBHardware` refuses the pretend iPhone's identifiers). Lookups use JTKit's demo connections "Contoso Jamf Pro (Demo)" and "Contoso Academy (Demo)" (`JamfStore.demoChoice`), and the Apple lookup the demo organization "Contoso (Demo)" (`AppleBusinessStore.demoChoice`), which has the pretend iPhone.
- Under tests: JTKit's `TestRun.isActive` (the unit-test host and a sandbox launch, which the UI tests use); `UnderTest` holds the app's folder and refusal text. `USBGuard` makes `LiveUSBHardware` refuse every call (after the pretend-iPhone check), with second safeguards in `Configurator`'s process launch, the administrator `--vdm` prompt and `MyApp.main`. `USBDeviceMonitor` doesn't watch real USB. `TestRun.refusingSession` refuses every request of a store holding the saved connections (Jamf and Apple; `AppleBusinessStore` takes the attempt log as `underTestLog`, and `AppConnectionStore(countsAsSaved:)` lets a test stand in for the saved list) (failing with `URLError(.resourceUnavailable)`). Each attempt is written to `$TMPDIR/SerialNumberReader-under-test/` (`TestRun.AttemptLog.usb` and `.savedConnections`).

From JTKit: `JamfPlatform.Client` (Jamf Pro direct and through the gateway), the `JamfPro` lookups and asset-tag calls, `JamfSchool.Client`, `ABM.Client` (sign-in, token, rate limit, the read calls; the app uses only `device`, `assignedServerID`, `mdmServers`, `appleCareCoverage` and `testConnection`), `RequestRecorder`, `JamfRegion`, `JamfPlatform.APIError`/`JamfSchool.APIError`, `ConnectionStore` + `ConnectionsSettingsTab` + `ConnectionRole` + `ConnectionPicker` + `ConnectionCommands`, `KeychainSecretStore`, `ActivityLog` + `ActivityLogWindow`, `SettingsWindow`, `AboutWindow` + `Acknowledgement`, `UpdateChecker`. Tests use `MockServer` from `JTKitTestSupport`.

App-specific, stays here: everything USB, lockdown, VDM, cfgutil and restore; `JamfDeviceRecord` (mapped from JTKit's records) and the app's hints.

When something is needed that JTKit could share, extend JTKit instead of adding another copy here.

Build facts: not sandboxed (`ENABLE_APP_SANDBOX = NO`, needed for IOKit and the root VDM path), hardened runtime, Swift 5 language mode with main-actor default isolation. It uses private interfaces (AppleHPM, `SecIdentityCreate`), so it can never go in the App Store.

## Rules

- **No real device identifiers anywhere in the repo** (it is public): no real serial numbers, UDIDs, ECIDs or device names containing them in code, tests, comments, fixtures or commit messages. Copy hardware output only after replacing the values with obvious placeholders. Before every commit, scan the staged diff for anything that looks like a real identifier and for Platform API credentials. Don't bring up identifiers already in the git history.
- **The app must never require trust.** macOS always shows "Trust This Computer?" on connect; that is normal, not caused by the app. Don't flag it or ask for trust tests. Only Enter Recovery on iOS 27 uses an existing pairing.
- System-log (`os.Logger`) messages that can hold an identifier or a server answer are `.private`.
- Every USB action that ran (Restart, Enter DFU, Enter Recovery, Boot to Normal, Restore, Revive, Remove Trust) writes an "Action" entry to the activity log, done or failed, with the device's identifiers for the masked export. A cancelled administrator prompt writes nothing.
- Tips in the app say only what a public Apple page supports, and link that page (decided by Jordy on 2026-11-10): the Mac DFU tips follow support.apple.com/108900 and /120694 and show only while the Mac is in Recovery.
- The app sends no MDM commands; all actions go over USB. Toward Apple Business and Apple School Manager it only reads: GET requests and the token request, never an activity (assign, release).
- **Demo mode never reaches a real device:** while it is on, `USBDeviceMonitor` doesn't watch USB (real devices are hidden, the sidebar says so) and every action, Restore and Revive goes to `DemoUSB`; a real device is refused, and outside demo mode the pretend iPhone is refused (`DemoModeTests`). Anything new that touches a device goes through `USBHardware`. The Demo Mode switch is dimmed while an action or restore runs. Test Connection stays real.
- Restore: one device at a time; the confirmation has Cancel as default and a destructive "Erase & Restore"; the IPSW is checked against the model and Apple's signing status before anything is erased; quitting during a restore warns.
- Restart / Enter DFU go only to the selected device's own USB-C port (decided by Jordy on 2026-11-10, docs/usb-c-port-targeting.md). The app passes the device's registry entry ID; the root helper follows the chain itself (`USBCPort`: an Apple device, its direct parent a root port with no hub above, `UsbIOPort` resolving to a `Port-USB-C@N` with a connection and a matching `usb-c-port-number`, leading to exactly one AppleHPM service), opens no other port, and checks the chain again just before sending (exit 5 when refused or changed). An incomplete chain (hub, dock, adapter, a Mac model without the property) is refused with "connect the device directly". The UI offers them for every device whose own port is known, whatever else is connected, and runs the same check without the password to dim the buttons with the reason. The helper accepts only the form with a device (decided by Jordy on 2026-11-10: the app has no button for a target without a USB entry, so the old "exactly one connected port" form is gone). The walk up the registry must reach its root, or nothing above is proven and it refuses. On an Intel Mac, and while the app runs under Rosetta, both are unavailable (app and helper check `hw.optional.arm64` and `sysctl.proc_translated`). A dimmed button's tooltip gives the short reason (`USBCPort.Refusal.shortReason`), the note under the buttons the full one; the detail view re-reads the port every 2 seconds, never while drawing.
- After Restart, Enter DFU and Restore, success only once the same ECID is back in the expected mode (`DeviceReturnWatch`; the restore OS 0x12AC never counts). The wait after Restart and Enter DFU holds nothing up: once the command is sent, other devices can be used, and the bar says how long the app waits (30 seconds for Enter DFU, 2 minutes for Restart) with Stop Waiting (decided by Jordy on 2026-11-10). A device that may stay off USB although the Restart worked (a booted iPhone or iPad until unlocked; a device in Recovery or DFU whose model isn't known, which may be a Mac) ends in orange, "Sent; unlock the device to see it again", logged as a warning (sent, not confirmed), never as failed; so does Stop Waiting, and a device back without a readable ECID. Not back in DFU mode after Enter DFU, or in Recovery after a known device's Restart, is failed. After a missed VDM reply (helper exit 6) the app watches 30 seconds. Not for a known Mac's Restart or Restore (a booted Mac never appears) nor a Revive (a device with a passcode stays off USB until unlocked).
- Privileged path trust model: before the `osascript` prompt, `DeviceActionController.signatureRefusal` checks that the app bundle on disk is valid, meets the running app's designated requirement, and that the executable to elevate is that bundle's own. A swap between that check and the prompt remains possible (a narrow window); the root side (`MyApp.main` → `PrivilegedVDM` → `VDMTool`) accepts only `--vdm reboot|dfu --entry <1–16 hex digits>`; any other use of `--vdm` exits without starting the GUI.
- Network use: only the Jamf servers, GitHub (update check), ipsw.me (model identifier and build only), and Apple Business and Apple School Manager only when an Apple account is saved: `account.apple.com` for sign-in, `api-business.apple.com` and `api-school.apple.com` for lookups, always through JTKit's `ABM.Client` (decided by Jordy on 2026-11-10). Keep it that way.
- The Platform API connection is environment-scoped only (no tenant-ID option). Default region: EU.
- **Preserve stored data:** Jamf connections as JSON under UserDefaults `jamfConnections` (format unchanged, so older versions keep reading it; the one in use under `activeJamfConnectionID`); their secrets in Keychain service `be.jordythery.SerialNumberReader.jamf`. Apple accounts as JSON under `appleBusinessConnections` (the one in use under `activeAppleBusinessConnectionID`); their private keys in Keychain service `be.jordythery.SerialNumberReader.appleBusiness`, account = the connection's UUID. The client ID and key ID are saved with the account, like a Jamf client ID; the private key and the client ID are never logged or exported. Never rename these keys or services. The pre-connections keys (`jamfServerURL`, `jamfAuthMethod`, …) and their Keychain items are only read once by `LegacySettingsConversion` (flag `jamfConnectionsConverted`), never changed or deleted.
- Credits: Restart / Enter DFU derive from macvdmtool and ThunderboltPatcher (Apache-2.0). The license in About must stay identical to `THIRD-PARTY-NOTICES.md` (a test checks it). No other third-party code in the app itself; ask Jordy before adding any.

## USB, lockdown and cfgutil facts (verified on hardware)

- **Before first unlock (BFU)** a booted iPhone/iPad doesn't appear on USB at all (USB restricted mode), not in Finder or Configurator either. Not an app bug: ask whether it was unlocked once since boot. Recovery and DFU always enumerate, whatever the lock state.
- **Product IDs** (vendor 0x05AC): Recovery 0x1281 (descriptor has the serial, SRNM, and ECID); classic DFU 0x1227 (descriptor with CPID/ECID, older devices); normal mode 0x1290–0x12AF.
- **Current hardware in DFU** (verified on iPhone 17e, M3 iPad Air, Apple Silicon Mac, macOS 26 host) shows up as "Debug USB" 0x1881: no serial descriptor, no identifiers, access needs a private Apple entitlement. The app can only detect presence (`isOpaqueDFU`) and guides the user to Recovery, where the serial is readable.
- A booted Mac never appears (it is a USB host).
- **Unpaired lockdown reads work** while the trust prompt is open: ProductType, ProductVersion, BuildVersion, DeviceClass, DeviceName. SerialNumber, ModelNumber and RegionInfo are refused (GetProhibited). ProductName says "iPhone OS" on every device, so the OS name comes from DeviceClass.
- **Enter Recovery on iOS/iPadOS 27:** an unpaired `EnterRecovery` is refused with `SessionInactive` (worked on iOS 26). It works over a paired session: usbmuxd `ReadPairRecord` (no root) → lockdown `StartSession` {HostID, SystemBUID} → `EnableSessionSSL` → TLS with the pair record's host certificate and key; since the release gate of 2026-10-31 the device's certificate is checked against the pair record (to be confirmed on hardware) → `EnterRecovery`. Secure Transport is used for the TLS; the client identity is built with `SecIdentityCreate` via `dlsym`. Pair records hold PKCS#8 keys; `SecKeyCreateWithData` needs PKCS#1.
- **Boot to Normal** from Recovery: iBoot control transfers `setenv auto-boot true`, `saveenv`, `reboot`. A send error on `reboot` means success (the device detaches). Works on iOS 27.
- **VDM actions** (AppleHPM) exist only for reboot and DFU, need root, Apple silicon and a USB-C target (Lightning devices can't). The USB root port's `UsbIOPort` names its physical port (`…/Port-USB-C@N`; `usb-c-port-number` is little-endian data), which walks up to its AppleHPM service (verified on an M3 Pro MacBook Pro, macOS 27.2.1, 2026-11-11: normal mode, Recovery, Debug USB DFU and a Mac target, on every USB-C port; a hub and a Thunderbolt dock are refused; classic DFU 0x1227 and other host models still to confirm). After a Restart from DFU a locked iPhone starts up out of sight (BFU), so the app reports "not confirmed", as designed. The app re-launches its own binary with `--vdm <reboot|dfu> --entry <hex>` through `osascript … with administrator privileges`, handled in `MyApp.main()` before the GUI starts; osascript returns -128 when the prompt is cancelled. "Recovery" in tools like DFU Blaster is lockdown `EnterRecovery`, not a VDM.
- **cfgutil** (inside Apple Configurator, no admin password needed): `--format JSON list` identifies devices in every mode, including opaque DFU (ECID, UDID, deviceType, locationID). Link to the USB device by ECID/UDID; use locationID only for DFU (it once differed for a booted device). cfgutil has no enter-recovery command.
- `cfgutil --progress --format JSON -e <ECID> restore|revive` writes JSON Lines: `Step`/`StepComplete`, `Progress` 0…1 (only while unzipping; -1 = indeterminate), then `CommandOutput`. Exit 0 = success. Reboots and disconnects during the job are expected.
- **Revive keeps data**, from DFU and from Recovery. During a revive the device goes DFU → Recovery 0x1281 (this stage has no SRNM) → restore OS 0x12AC → normal, so "Enter DFU → Revive" can't be used to read the serial.
- Apple stops signing older OS versions quickly; downgrades are impossible, and old-OS test devices can't be restored to that OS again.

## Testing

- Unit tests: Swift Testing in `Serial Number Reader Tests`, ⌘U in the app's project. They cover the descriptor parser, UDIDs and ECIDs, cfgutil output, IPSW checks, connection conversion, Jamf networking (on JTKit's `MockServer`), the Apple Business and Apple School Manager lookup on a fake Apple (`AppleBusinessTests`: sign-in and signature, only GETs and the token request to Apple's hosts, the two lists and Keychain stores kept apart, the roles, the status look, demo mode, the private key and client ID kept out of logs, the order number and reseller ID masked in the bug-report export, the two lists loading apart), session export, the action log entries, the USB-C port chain and the root helper's arguments on made-up registry data (`USBCPortTests`, `PrivilegedVDMTests`: every refusal), waiting for the same device to come back (`DeviceReturnTests`) and the acknowledgement.
- As the unit-test host, the app uses a throwaway UserDefaults domain and no Keychain (`AppConnectionStore.forUnitTestHost()`, for both lists), so tests never touch real saved connections. The connection-conversion suite is `.serialized`.
- USB, lockdown, VDM and restore can't run in tests or the dev harness; they need a real device. Jordy checks them by hand.
- **Under tests nothing reaches a real USB device or a saved connection** (decided by Jordy, JTKit ROADMAP step 11): no USB action (Restart, Enter DFU, Enter Recovery, Boot to Normal, Restore, Revive, Remove Trust), no lockdown read, no USB-C port check, no `cfgutil`, also with a device plugged in; no request for a saved connection, sign-in included; no update check. Every attempt is refused before anything happens and recorded (`TestRun`, `UnderTest`, `UnderTestTests`); the release check fails on any.
- Test data uses placeholder identifiers and `example.jamfcloud.com`-style hosts only.
- Never run the long UI suites of Jamf Deployer or AppSettings2Blueprint unless Jordy asks for one by name.
- UI tests: `Serial Number Reader UITests`: `DemoSmokeUITests` (JTKit's `JTKitUITestSupport`, demo mode, every main feature Demo Mode can exercise, including the pretend iPhone's Apple section and an Apple account with its role in Settings › Connections) and `LiveUITests` (the live-check switch: Test Connection in Settings › Connections on jamfpro-readonly, jamfschool-readonly and jamf-test-a; nothing else, never a USB action or device command). The app's own scheme runs the unit tests only.
- Under the live-check switch (`LiveLaunch`) the connection store holds only the release check's connections (`AppConnection.live`: `JamfConnection(live:)`, or `AppleBusinessConnection(live:)` for an Apple service; there is none today), in both lists, the old-settings conversion doesn't run, and a session export goes to `LiveLaunch.appFilesFolder("Exports")`.
- **Release check** (`Scripts/release-check.sh`, scheme "Serial Number Reader Release Check"; JTKit ROADMAP step 11), run unattended by Claude:
  - Live checks (`LiveCheckTests.swift`, skipped on ⌘U): on jamfpro-readonly (Jamf Pro over the Platform API) and jamfschool-readonly one serial is taken from the tenant's own inventory at run time, kept in memory only and masked in the report ("serial 1"); the app's own `JamfStore` lookup must find it. Reads only. An empty inventory is reported as "nothing to look up" with the counts, not as a failure (decided by Jordy; jamfpro-readonly has no devices). jamfpro-production the same, only with `--include-production`.
  - On jamf-test-a (Platform API), after the read-only lookups: the test code creates one unmanaged `JTKTEST SN … – iPad` mobile device record with a made-up serial (`JTKTEST…`) and UDID and no model or OS, like a record that never enrolled, and an unmanaged `JTKTEST SN … – Mac` computer record (made-up serial `JTKTESTM…`). The `fail-live-step` fault point comes after both exist. The app's lookup finds the iPad and shows its name; its own Save changes the asset tag behind a fence (reads, sign-in and that one PATCH only); the test code and the app read the tag and name back. The app's lookup finds the Mac as a computer. Cleanup deletes both and sweeps `JTKTEST` mobile device and computer records. Never written: the read-only tenants.
  - A record that never enrolled gets device type "Unknown", and Jamf's device list leaves out its general section (name, asset tag); since JTKit 0.12.3 it is read from the record itself, and this check confirms the app shows both.
  - Steps "no USB action or cfgutil under tests" and "no request to a saved connection under tests" at the start, around the live steps and at the end; any attempt fails the run.
  - `--fault usb-attempt` sends one Restart through the real doorway to show the guard refuses it and the run fails; it starts only when `ioreg` lists no Apple device in a device mode.
  - No live check against a real Apple organization yet (an idea in ROADMAP.md); the Apple lookup is checked on a fake Apple and in demo mode, and an Apple account under tests is refused like a Jamf connection (`UnderTestTests`).
  - Fingerprint (hashes only): `jamfConnections` and its backup, `activeJamfConnectionID`, `appleBusinessConnections` and its backup, `activeAppleBusinessConnectionID`, `demoMode`, `jamfConnectionsConverted` and the legacy keys, the Keychain item names under `be.jordythery.SerialNumberReader.jamf` and `be.jordythery.SerialNumberReader.appleBusiness`, and the folders where an activity log would appear on disk (it lives in memory only; they must stay absent).

## Releasing

1. Bump `MARKETING_VERSION` and `CURRENT_PROJECT_VERSION` in the project.
2. Update the README if features changed (its screenshot must show no real identifiers).
3. Archive from the app's own project, sign with Developer ID, notarize, and zip.
4. Tag `vX.Y.Z`, create the GitHub release with notes (the in-app updater shows them) and attach the zip. Release notes (CHANGELOG entries and GitHub release notes) are for the end user: professional and concise, saying what changed for them, and never mentioning the release check, reviews, tests, test targets, AI tools, JTKit step numbers or how a problem was found (decided by Jordy on 2026-11-01).
5. Website: follow ../jordythery.be/CLAUDE.md, section “When an app is released”. Every release checks this app's card on apps.html, and its own page if it has one, against the released README and CHANGELOG, and changes them on a branch with a pull request. Jordy merges, which publishes the site.

Before any of this, follow the release gate in JTKit/ROADMAP.md.
